# HallPass Offline Arcade — design

This document records the plan that was written before the code (AGENTS.md
phases 1 and 2) and the decisions behind it. The product brief was the
"HallPass Offline Arcade — Custom Game Package System" prompt of 14 Nov 2026.
The package format itself is specified separately in `hpg-format.md`. How to
add a game is covered in `offline-arcade-games.md`.

## 1. What is built

A player opens `/offline-arcade`, ticks the games they want and presses **Build
my arcade**. They receive `hallpass-offline-arcade.zip`, which contains:

- `index.html`: the whole launcher in one file, with no network use.
- `games.zip`: one `.hpg` file per selected game.
- `README.txt`: three lines explaining how to start.

The player extracts the ZIP, double-clicks `index.html` (it opens over `file://`
in Chrome, Edge or Firefox) and imports `games.zip`. The games then appear in a
library and play fully offline. Nothing needs installing, no server is involved
and there is no account.

## 2. Decisions

Taken with the owner on 14 Nov 2026:

- **Packages and the launcher are built on every deploy.** This happens in
  `prebuild`, after `sync-games`, into `public/arcade/`, which is gitignored. The
  packages therefore always match the game files that ship.
- **Unverified packages are refused.** The launcher embeds the SHA-256 of every
  `manifest.json` built in the same deploy, and imports only packages whose
  manifest matches one of those digests. Each manifest in turn lists the SHA-256
  of every file in its package, so verification runs from the launcher, to the
  manifest, to each file. A package from a newer deploy is refused with a "get a
  fresh arcade" message, because a user downloads the launcher and the packages
  together.
- **The builder is linked from the site footer**, not from the main navigation,
  while it is new.

Engineering decisions, each forced by behaviour tested in a real browser over
`file://` (spike of 14 Nov, Chrome 14x stable on macOS; Firefox is §7):

- **Games run in `<iframe sandbox="allow-scripts allow-pointer-lock" srcdoc>`
  and never get `allow-same-origin`.** The frame's origin is opaque (`null`),
  so it cannot reach `window.parent`, the launcher's storage or its DOM. That
  was verified in the spike: `parent.document` throws SecurityError.
- **Opaque origins have no storage.** Inside the frame, `localStorage`,
  `indexedDB` and `document.cookie` all throw SecurityError. Many HallPass games
  use `localStorage`, so the in-frame bootstrap swaps in a
  launcher-backed `localStorage` and `sessionStorage`. The spike verified that
  `Object.defineProperty(window, "localStorage", …)` works. This is also how saves
  pass through the launcher's save API instead of browser storage.
- **The frame cannot load blob URLs created by the launcher.** Chrome reports "Not
  allowed to load local resource: blob:null/…". All game bytes therefore travel
  inside the `srcdoc` document. Any blob URL the game needs is created *inside*
  the frame, where Chrome accepts it as an image, a script, a fetch target or a
  classic worker.
- **Module workers from blobs fail in the frame; classic workers work.** The
  packager rebuilds every worker as a classic IIFE script. The bootstrap wraps
  `Worker`, resolves `hpg:/…` URLs from the package, and drops
  `type: "module"` for workers it built itself.
- **WebAssembly works in the frame.** Both `instantiate` and
  `instantiateStreaming` of a frame-made blob succeed, so WASM modules ship as
  separate package files fetched through `hpg:/…`. **No current HallPass game uses
  WASM**: the only match in the audit is a `system-restore` upgrade *named*
  "WebAssembly". The WASM path is proven with a real compiled test module, and no
  JS game is described as WASM.
- **The ZIP is assembled in the player's browser** from static, prebuilt `.hpg`
  files. The server does no CPU work, writes no temp files and recompiles
  nothing.
- **The launcher is vanilla TypeScript and CSS**, bundled by esbuild into one HTML
  file. React would add about 140 KB to a page that has a handful of screens.
  esbuild is already installed (via tsup), so it becomes an explicit
  devDependency at the installed version. Vite and `vite-plugin-singlefile`
  are *not* added: esbuild plus a template does the same job with no new
  framework.
- **HTML is parsed with jsdom** (already a devDependency), never with regular
  expressions. JS and CSS are bundled and minified by esbuild. No source maps are
  written.
- **Playwright stays opt-in**, following `sdk/p2p/e2e/run.mjs`: the browser
  journey script loads `playwright-core` from `PLAYWRIGHT_CORE`.

34 games are present in `public/games/`. The audit is regenerated by
`npm run hpg:audit`. Most games are one inline HTML file plus `cover.png`;
`conquest` and `ragdoll-hoops` are Vite builds with module scripts.

About 20 games load `/sdk/v1/hallpass.js`. Offline, the packager removes that tag
and the bootstrap provides an offline SDK: scores go to a local leaderboard
held by the launcher, and every other call settles with its documented
inert result.

**First three games:** `conquest` (Vite modules, CSS, a module worker, dynamic
import, the SDK and saves), `neon-tether` (canvas, audio, the SDK and
`localStorage`) and `depths-of-aethelgard` (canvas, audio, the SDK and saves).

## 4. Excluded from version 1

- Package signing with a private key. The digest list embedded in the launcher
  is the trust anchor (see §2). Ed25519 signing is noted as future work.
- Vendoring Tailwind Play and Three.js for the CDN-dependent games.
- Network multiplayer (`last-bell`). This is not deferred: it is incompatible
  with offline play.
- Edge and Firefox test runs. Edge is not installed on the development
  machine, and its Playwright Firefox would not install (§7). Both are
  reported as untested rather than assumed to work.

## 5. Implementation plan

Layout: `hpg/` at the repo root, a sibling of `sdk/`.

```
hpg/src/format/    manifest schema + validation, safe paths, semver   (shared)
hpg/src/archive/   bounded unzip, zip writer, package read/verify,
                   collection import (games.zip | .hpg)                (shared)
hpg/src/protocol/  postMessage envelope + validators                  (shared)
hpg/src/guest/     in-frame bootstrap: storage shim, hpg:/ VFS,
                   Worker/fetch wrap, offline SDK, events, mute        (browser)
hpg/src/host/      GameSession (iframe lifecycle), SaveStore,
                   PackageLibrary (IndexedDB | memory)                 (browser)
hpg/src/launcher/  UI, styles, HTML template                          (browser)
hpg/src/build/     adapters, HTML inliner, esbuild, packager, audit,
                   launcher build, arcade output                       (node)
hpg/src/cli/       build | inspect | validate | audit | arcade         (node)
hpg/games.config.ts  one adapter entry per offline game
hpg/e2e/run.mjs      real-browser file:// journey (opt-in Playwright)
scripts/hpg.mjs      bundles the CLI with esbuild and runs it
```

The npm scripts are `hpg:build`, `hpg:inspect`, `hpg:validate`, `hpg:audit`,
`hpg:arcade` (all packages, launcher and catalog into `public/arcade/`) and
`hpg:e2e`. `prebuild` and `predev` gain `npm run hpg:arcade`.

If a game fails to package, it is left out of the catalog and the build prints a
`::warning::`. The site deploy continues and the catalog lists only packages
that were actually built.

Commit order:

1. This design document.
2. Format: manifest types and validation, path rules, semver, the `hpg-format.md`
   spec, and tests.
3. Archive: bounded unzip (limits on entry count, size and ratio, plus path
   checks), package read and verify, collection import (duplicates, partial
   failure), and tests.
4. Protocol and guest bootstrap, with tests.
5. Host runtime: game session, save store (IndexedDB or memory, versioned
   export and import) and package library, with tests covering cleanup.
6. Packager: adapters, jsdom inliner, esbuild bundling, CLI, runner and npm
   scripts, with fixture tests.
7. The first three game adapters.
8. Launcher build and UI: first launch, import, library and player.
9. Saves UI, persistence messaging and save export and import.
10. `public/arcade` output: catalog, trust list, `prebuild` and `.gitignore`.
11. The real-browser e2e journey over `file://` with the network blocked.
12. The `/offline-arcade` builder page and the footer link.
13. Documentation: adding games and the compatibility report.
14. Phase G fixes and more games, as the browser runs dictate.

## 6. Security boundaries

This is a packaging format, not DRM. Minification and ZIP compression stop
casual reading of loose files and nothing more. Packages never contain secrets:
the packager only reads `public/games/<slug>/`, which is already served publicly.
Game code is isolated by the opaque-origin sandbox. Every message from a game is
untrusted input: the launcher checks `event.source` against the active frame,
`event.origin === "null"`, the session nonce, the message shape and size limits.
The nonce only filters out stale frames. It is not a secret from the game,
because the game and the bootstrap share one frame.

## 7. Browser results

From `npm run hpg:e2e` on 14 November 2026 (macOS, Playwright 1.56.1), the
launcher opened from `file://` with the browser's network off. The checks are
listed in `offline-arcade-games.md` ("Browser testing").

| Browser | Result | Notes |
|---|---|---|
| Google Chrome 157 | **45/45 passed** | All three games: start, draw, react to real input, are sandboxed and keep saves across Back, relaunch and a browser restart. Zero network requests. One known test limitation, below. |
| Firefox | **Not tested** | The Playwright Firefox build on this machine is incomplete (`libmozglue.dylib` missing), and two reinstalls stalled during unpacking. Nothing here is Chrome-specific by design, but that is unproven. |
| Edge | **Not tested** | Not installed. Edge is Chromium-based, so Chrome's result is the best indication, but it is not a result. |
| Safari | Not a target | Not tested. |

Also checked by hand in Chrome: the website download → unzip → open
`index.html` from disk with the network off → import → play chain, end to
end; `/offline-arcade` in light, dark and at phone width (no horizontal
scroll); and the size estimate (195 KB estimated, 196 KB downloaded for all
three games).

**Known test limitation.** Headless Chrome stops routing real mouse input into
an out-of-process sandboxed frame after a canvas there captured the pointer.
Conquest's map does this, so the e2e presses Conquest's Start with a DOM click
after a real tap has enabled it. Headed Chrome starts the match from a real
click (checked with `HEADED=1`).

**Before calling Firefox or Edge supported:** run
`BROWSER=firefox npm run hpg:e2e` and `BROWSER=edge npm run hpg:e2e` on a
machine that has them.
