# HallPass mobile — making the launch splash actually load something

`MobileSplash` used to show a wordmark and a spinning wheel for 700ms and then
fade. It was honest about what it was for — covering the second-paint seam where
the desktop layout swaps to the phone shell — and it deliberately did **not**
kick off a service-worker sync (see the long note in `MobileSplash.tsx`, and do
not undo that reasoning).

But it was a loading screen that loaded nothing. This is the record of giving it
real work: warm the two surfaces a phone visitor reaches next (Friends and You),
and warm the images the shell is about to paint, inside the window where the
visitor is already waiting.

> **Status — built, on `claude/mobile-preloading-plan-ojq5zh`.**
>
> Seven commits, `lint` / `test` / `build` green (1023 tests). What has **not**
> been done is the on-device pass: everything in "Still owed" below is a
> production-only behaviour that cannot be observed from a dev container, and one
> of them decides whether a third of this change is worth keeping.

---

## Scope

**In, and shipped:**

- `app/lib/mobile-preload.ts` — a client-only image preloader with dedupe, a
  connection budget, and a synchronous "how many are still in flight" count.
- Cover preloading for the phone catalogue, driven from `MobileCatalog` in
  `Arcade.tsx` (the only component that knows the games and their order).
- `app/lib/social-cache.ts` — an in-memory, TTL'd store for
  `/api/v1/me/friends` and `/api/v1/me/challenges`, warmed at launch and read by
  `FriendsIsland`.
- Friends' **avatars** preloaded off the back of that warm-up — cross-origin
  Google URLs that nothing in this app caches.
- `router.prefetch()` of `/play/you` and `/play/you/friends` from the splash.
- The splash's dismissal tied — floor, poll, hard ceiling — to the first screen
  of covers being ready.

**Out — deliberately:**

- **No service-worker involvement.** No `SYNC_NOW`, no new precache entries, no
  touching `scripts/build-sw-manifest.mjs`. `MobileSplash.tsx` documents why the
  splash must not drive the SW, and native covers are already precached anyway.
  (`public/sw-manifest.js` is regenerated by any local `npm run build`; that churn
  is a deploy artifact and was deliberately not committed here.)
- **No shared `/api/v1/me` cache.** Four components fetch that endpoint
  independently on every page (`AccountMenu`, `WelcomeToast`, `ReviewComposer`,
  `FeaturePromo`) and deduping them is an obvious win — but it is a site-wide
  refactor with desktop blast radius, not mobile preloading. It is the follow-up.
- **No `staleTimes` config change.** Raising `experimental.staleTimes.dynamic`
  would extend the client cache for every dynamic route, personal pages included,
  so a player would see stale badges and standings. The explicit `router.prefetch`
  gets the same effect for the two routes that need it.
- **No preloading on desktop, and nothing outside the once-per-session latch.**
- **No change to any prerendered HTML.** Everything happens in effects, on the
  second paint, on a device that matched `(pointer: coarse) and (hover: none)`.

## What this actually buys — measured, not assumed

One of the three strands is much smaller than it sounds, and the plan should not
oversell it.

### Covers: small today, and here is why

`mobileCatalog()` is strict — only games a human confirmed play on a phone. In
`app/lib/games.ts` today that is **3 of 30** static games. Three cards in a
two-column grid are all above the fold, so the browser already loads them without
help.

So the cover strand buys:

- **A readiness signal.** `new Image()` on a URL the DOM is already requesting
  dedupes to the same fetch — it costs nothing and gives the splash an `onload`
  to wait for. This is the main reason it exists.
- **Below-the-fold covers**, which `GameCard` renders `loading="lazy"` and the
  browser does not request until you scroll. Worth ~nothing at 3 games and real
  time at 30, which is where Phase 6 of `mobile.md` is heading.
- **External / override covers.** `coverUrl` points at Vercel Blob for external
  games and for any dashboard override, and `scripts/build-sw-manifest.mjs` only
  sweeps `public/games/**`, so those are a cold fetch every time.

### Friends: the big one

`FriendsIsland` rendered `null` until `/api/v1/me/friends` resolved. So tapping
the Friends tab was: a dynamic navigation (server: `auth()` + Neon), then the
island mounts, then **two more round trips** before a single pixel of content.
Warming both responses during the splash means the tab paints from memory.

### You: a real gap in what the tab bar already does

`MobileTabBar` links use the default `prefetch` (`auto`). Per
`node_modules/next/dist/docs/01-app/03-api-reference/02-components/link.md`, for a
**dynamic** route that fetches only "the partial route down to the nearest segment
with a `loading.js` boundary" — and per
`.../05-config/01-next-config-js/staleTimes.md` the dynamic client-cache period
defaults to **0 seconds**, with only the loading boundary reusable for the static
period. `/play/you`'s layout is `auth()`-gated and dynamic (the build confirms it:
both routes print as `ƒ`), and `app/play/you/loading.tsx` already documents that
the layout is not covered by its own fallback — so the tap still blocks on the
layout's server render.

The same `staleTimes` page says the **static** period (5 min default) applies
"when the `prefetch` prop on `Link` is set to `true`, or when calling
`router.prefetch`". That is the difference this uses: one explicit call per route,
once per session, instead of a config change.

**This is a claim about framework behaviour, not about this codebase, and it has
not been observed yet.** See "Still owed".

## What was built, commit by commit

### 1. `app/lib/mobile-preload.ts`

```ts
export const FIRST_SCREEN_COUNT = 6;
export type PreloadBudget = "first-screen" | "all";
export function preloadBudget(conn?: ConnectionHint | null): PreloadBudget;
export function readConnection(): ConnectionHint | null;
export function coverUrls(games: readonly CoverGame[]): string[];
export function preloadImages(urls, opts?: { firstScreen?, referrerPolicy? }): void;
export function pendingFirstScreen(): number;
```

Decisions worth keeping:

- **The budget is two-valued, not three.** The plan had a `"none"`; nothing ever
  returned it, and a value nothing returns is a lie in the type. `"first-screen"`
  IS the free tier — the images the browser fetches anyway.
- **A missing `navigator.connection` means `"all"`.** Safari implements none of
  it, so every iPhone lands there; absence of the API is not evidence of a bad
  connection. `saveData` and the 2g tiers narrow instead.
- **`referrerPolicy` is a parameter and is set before `src`.** `Avatar.tsx` is
  explicit that fetching a Google-hosted avatar without `no-referrer` leaks the
  page the viewer is on. Assigning `src` starts the request, so a policy set
  afterwards would arrive too late.
- **`decode()` before settling.** "In the cache" is not "paints without a beat".
- **`pendingFirstScreen()` is a count, not a promise.** The splash polls it. A
  promise it awaits is a promise that can strand it — the failure `MobileSplash`
  already carries a docblock about.
- **Deviation from the plan:** the planned `firstScreenCovers(favorites, rest)`
  became `coverUrls(games)` plus `FIRST_SCREEN_COUNT`, with the slicing at the
  call site. The lib decides what a cover URL is; the shell decides what is on
  screen first, which is the shell's business.

### 2. Covers, from `MobileCatalog`

One effect, in the component that only renders on a phone, preloading
`[...favorites, ...rest]` in paint order: the first `FIRST_SCREEN_COUNT` counted
so the splash can wait, the remainder fire-and-forget and skipped entirely when
the budget says `"first-screen"`. URLs come from `coverImageSrc()` — the one
definition of where cover art lives — so a gradient-only external game yields
`null` and is skipped rather than requesting a guaranteed 404.

The effect keys on the joined URLs rather than the arrays, which are rebuilt every
render; without that it would re-run on every keystroke in the search box. Repeat
runs are harmless regardless — `preloadImages` dedupes by URL.

### 3. `app/lib/social-cache.ts`

`useSyncExternalStore` in the shape `personalization.ts` documents: a cached
snapshot reference, and a stable `null` server snapshot so the island's SSR pass
is byte-identical to what it rendered before.

- **TTL 60s, enforced on write, never on read.** A `getSnapshot` whose answer
  changes with the clock and no notification is a torn render. A read always
  returns what is cached; the TTL only decides whether a warm-up refetches.
- **In memory only** — never `localStorage`, never a `Cache`. `/api/` is excluded
  from the service worker precisely so one player's friends list cannot outlive
  their session on a shared school machine.
- **A `signedIn: false` response drops the other endpoint's payload.** Signing out
  is a server action plus `redirect()` — a client transition, not a reload — so
  module state survives it. Nothing renders the island for a signed-out visitor
  today, so this leaks nothing as things stand; relying on a guard two components
  away is how that stops being true later.
- **⚠ Never import this from a server component.** Module state on the server is
  per-process and shared across requests.
- **Deviation:** `warmSocial()` returns a `Promise<void>` callers are meant to
  ignore. Two of its tests were passing without it — `fetch` is called
  synchronously and the write lands two microtasks later, so polling the call
  count let the second warm-up hit the in-flight dedupe and the freshness rule was
  never exercised.

### 4. `FriendsIsland` reads the store

Local `useState` for both responses replaced by `useCachedFriends()` /
`useCachedChallenges()`; `load` / `loadChallenges` became `refreshFriends` /
`refreshChallenges`, which write the store. It still revalidates on every mount,
cached or not. Cold behaviour is unchanged: no cache, no paint, then a fetch.

### 5. The splash triggers the warm-up

Inside the existing effect, after the `sessionStorage` latch is taken — so it
inherits "phones only, once per session, not on `SKIP_PREFIXES`" for free:
`warmSocial()`, then `router.prefetch` for both tab routes. Not gated on being
signed in: a signed-out prefetch stops at `auth()` returning null with no Neon
behind it, and finding out first would cost the round trip this avoids.

Prefetching is production-only, so none of it is visible under `npm run dev`.

### 6. The splash waits for what it started

Floor 700ms → poll `pendingFirstScreen()` every 100ms → hard ceiling 1600ms, with
the ceiling scheduled **first and unconditionally**, before any of the work it
might wait on exists. That ordering is the guarantee: no hung request, 404 cover
or page that never registers a catalogue can leave the overlay up, and the worst
case is the old fixed behaviour arriving late rather than never. It waits only on
the covers about to be on screen — never on the friends fetch or the prefetches.

## Gotchas

1. **Nothing may change the first paint.** The mobile shell rests on the server
   render and the first client render being byte-identical to the prerendered,
   SW-precached HTML. Every hook here reads `null` before mount and every preload
   happens in an effect. The `useSyncExternalStore` server snapshot in the social
   cache is load-bearing for the same reason.
2. **A module-level cache is a per-process cache on the server.** Browser-only
   writes plus a `null` server snapshot are what make it safe; an innocent-looking
   import from a server component breaks both.
3. **The splash must never be able to hang.** The ceiling timer is scheduled
   before any work is registered, and `pendingFirstScreen()` is synchronous
   precisely so the exit path never awaits anything.
4. **`new Image()` on a URL the DOM already wants is free.** Same cache key, same
   in-flight request. The real cost is the below-the-fold covers and the avatars,
   which is what the budget check governs.
5. **Referrer policy on avatar preloads is not optional.** `Avatar.tsx` says why;
   a preload without it re-opens the leak from a different code path.
6. **Prefetching a dynamic route runs it on the server.** Two extra renders per
   phone launch, once per session, both cheap when signed out. If the
   `router.prefetch` claim does not verify, these are pure cost and commit 5's
   prefetch half should come back out.
7. **`/play/you` must stay in `isPrivatePath`.** The RSC prefetch is a GET to that
   pathname; `sw.js` returns early for it, so no personal payload enters
   `hp-runtime`. Removing that entry turns this feature into the leak both
   exclusion lists exist to prevent.

## Still owed — production, on a phone

None of this can be observed from a dev container: prefetching and the service
worker are both production-only, and the device query wants a real phone.

1. `npm run build && npm start`, then on a phone or emulation with the Network
   panel open:
   - launch cold → covers and both `/api/v1/me/*` calls go out **during** the
     splash, not after it;
   - tap Friends → the list paints immediately, with faces, and the island's
     revalidation is the only request on the wire;
   - tap You → **whether a server round trip happens**. This is the check that
     decides if the `router.prefetch` half of commit 5 survives.
2. Desktop, same build: no preloads, no prefetches, no splash — identical to
   before.
3. Sign out, then navigate to `/play/you/friends`: the not-signed-in card, and no
   trace of the previous session's list.
4. Throttled to "Slow 3G": the splash lifts at the ceiling, not later.
